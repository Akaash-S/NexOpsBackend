## 1. Redis Connection Pool Exhaustion & Automatic Failover Recovery

### Root Cause
Under high concurrency, the Redis client experienced connection ceiling errors (`WARNING | Redis cache read failed ... Too many connections`). Previously, once an exception occurred, a global flag `_use_in_memory = True` permanently locked the backend to in-memory fallback, even after Redis connectivity recovered.

### Solution & Code Fix
- Implemented `_check_redis_health()` with a 30-second backoff cooldown in [backend/app/core/redis.py](file:///d:/Projects/ReactJS/NexOps/backend/app/core/redis.py#L35).
- When Redis connection limits are reached, the system gracefully uses in-memory cache without crashing.
- Every 30 seconds, `_check_redis_health()` pings Redis; upon recovery, it automatically resumes Redis caching mode without server restarts.

## 2. PagerDuty HMAC Verification & Multi-Tenant Secret Isolation

### Root Cause
PagerDuty webhook requests returned `401 Unauthorized` (`Expected 21bbf5eb... received 1ba8b325...`). The server looked up user `np8ebZ6MwNZPeYJGQTzW4xRPAfj2`, found `user.pagerduty_webhook_secret` was `None`, and fell back to `PAGERDUTY_WEBHOOK_SECRET` on Render, which did not match the secret key generated by PagerDuty for the user's specific webhook subscription.

### Solution & Code Fix
- Added endpoint `POST /api/v1/integrations/pagerduty/secret` in [backend/app/api/routes/integrations.py](file:///d:/Projects/ReactJS/NexOps/backend/app/api/routes/integrations.py#L863) allowing users to encrypt & store their individual webhook secret in PostgreSQL.
- Enhanced `verify_pagerduty_signature()` in [backend/app/api/routes/webhooks.py](file:///d:/Projects/ReactJS/NexOps/backend/app/api/routes/webhooks.py#L60) to track secret source (`user:<id>` vs `global_env`) and output SHA-256 fingerprints (`secret_fp`) on HMAC verification failures for instant diagnostic visibility without exposing raw secrets.

## 3. Background Automation Task RLS Block

### Root Cause
PagerDuty webhooks returned `HTTP 200 OK` and enqueued events, but no incidents appeared on the dashboard. FastAPI `BackgroundTasks` executing `_run_automation(event_id)` opened a fresh database connection (`async_session()`). Because no HTTP user context existed on the background connection, PostgreSQL Row-Level Security (RLS) hid the event (`event` evaluated to `None`), skipping `process_event()` and preventing incident creation.

### Solution & Code Fix
- Wrapped `_run_automation()` in `async with rls_bypass(session):` in [backend/app/api/routes/events.py](file:///d:/Projects/ReactJS/NexOps/backend/app/api/routes/events.py#L20).
- Corrected import module path to `from app.core.rls import rls_bypass` (resolving `ImportError`).

## 4. Incident Duration Timezone Offset Discrepancy (`5h 31m` vs `1m`)

### Root Cause
Python generated naive ISO datetime strings without explicit timezone offsets (e.g. `"2026-08-14T14:35:00"`). In the frontend, JavaScript's `new Date(timestamp)` constructor parsed ISO strings lacking trailing `'Z'` as **local browser time (IST = UTC+5:30)**. Comparing 2:35 PM IST against current local time 8:05 PM IST resulted in an artificial **5 hours 30 minutes** duration offset.

### Solution & Code Fix
- Updated `calculateDuration()` in [updated-frontend/components/dashboard/active-incidents.tsx](file:///d:/Projects/ReactJS/NexOps/updated-frontend/components/dashboard/active-incidents.tsx#L35) to use `parseUTCDate()`, which appends `'Z'` to naive timestamps so JavaScript parses them as UTC.
- Updated [backend/app/services/automation_service.py](file:///d:/Projects/ReactJS/NexOps/backend/app/services/automation_service.py#L113) to append `'Z'` to ISO datetime fields in WebSocket payloads.

## 5. Repository Health Score & CI Status Parity (`82%` vs `45%`)

### Root Cause
The Dependencies Topology Page (`/dependencies/topology`) dynamically calculated `effective_health = min(health_score, 45.0)` and `effective_ci = "failing"` when an active incident existed. However, the Services Page (`/services` -> `GET /repos`) read raw `Repo.health_score` (`81.8%`) from PostgreSQL without applying active incident penalties.

### Solution & Code Fix
- Updated `calculate_health_score()` in [backend/app/services/insight_service.py](file:///d:/Projects/ReactJS/NexOps/backend/app/services/insight_service.py#L87) to check for active open/investigating incidents and cap health score at **`45.0%`** while setting `ci_status = "failing"`.
- Updated `get_repos()` in [backend/app/services/repo_service.py](file:///d:/Projects/ReactJS/NexOps/backend/app/services/repo_service.py#L49) to apply active incident health score parity across all service API endpoints.

## 6. Post-Login Redirect & Property Key Mismatch

### Root Cause
When users logged out and logged back in via Google/GitHub without refreshing the page, `onAuthStateChanged` in [updated-frontend/lib/hooks/use-app-state.tsx](file:///d:/Projects/ReactJS/NexOps/updated-frontend/lib/hooks/use-app-state.tsx#L170) attempted to read `dbUser.onboardingCompleted` (camelCase). Because PostgreSQL returns `onboarding_completed` (snake_case), the expression evaluated to `undefined || false` -> `false`. This set `onboardingComplete = false` and routed the user to `/onboarding` instead of `/dashboard` until a manual browser refresh (F5).

### Solution & Code Fix
- Updated `onAuthStateChanged` in [updated-frontend/lib/hooks/use-app-state.tsx](file:///d:/Projects/ReactJS/NexOps/updated-frontend/lib/hooks/use-app-state.tsx#L171) to read `dbUser.onboarding_completed ?? dbUser.onboardingCompleted ?? true` and populate `workspace_id`.
